# User workspace and listing photos

## Signed-in flow and role-based navigation

Visitors see the marketing landing page at `/`. Signed-in users never do: `/` redirects them (keeping any query string) to `/explore`, the map-only page, and login, social login, email verification and password confirmation all end there unless the user was sent to login from a specific page, in which case that page is restored. The browser PWA `start_url` stays `/`, so an installed app opens the map for signed-in users and the landing page for visitors. Logging out returns to the landing page. Signed-in users also lose the landing-page anchors (How it works, For providers, Support) from the header; the brand links to the map.

Every signed-in user gets **Map**, **Saved listings**, **Inbox**, **Calendar**, **Profile**, **Settings** and **Become a provider** (labelled **Provider roles** once approved). Inbox contains Messages and Requests, with sent and received request views for providers. **Dashboard** and **My listings** appear only after at least one provider role is approved (`auth.isProvider`, from `User::isApprovedProvider()`). `/dashboard` redirects everyone else to the map. `/my-listings` stays reachable by direct link so pending applicants can still use the draft flow described below. The link list lives in `resources/js/Components/Account/accountLinks.mjs`.

Email/password registration requires a birthdate and validates that the user is at least 18. This age check is not applied to social sign-in or existing accounts. Before accessing protected account features, users must complete their profile with birthdate, sex assigned at birth (including a "Prefer not to say" option), city and full address. Public browsing, profile editing, verification, legal acceptance, settings and logout remain available. City can appear publicly; birthdate, sex and address are omitted from public and shared user data. The authenticated `/api/v1/profile` endpoint exposes these fields to the account owner, and incomplete API accounts receive HTTP 428 with the profile endpoint. Mobile clients must implement this completion flow and send `birth_date` for email registration. Apply the personal-details migration before deploying the application.

On screens up to 700px wide, signed-in marketplace and account pages also show a bottom navigation bar for Map, Saved, Inbox, Calendar and More (Manage for approved providers). The quick menu provides profile and settings links, plus provider tools where applicable. Profile retains personal details and the profile photo. Settings contains connected sign-in accounts, password changes and account deletion. The bar accounts for the device's bottom safe area; the map and scrollable account pages reserve space for it.

On signed-in mobile marketplace pages, the header uses the Aadi logo instead of a duplicate Map link; the bottom bar provides the Map tab. The desktop header retains its Map link.

The visitor landing hero uses a Three.js scene that changes with the selected search category, with animated details for spaces, vehicles, and services. It can be rotated with a pointer or keyboard, and ambient motion can be paused; reduced-motion preferences are respected. If WebGL cannot initialize, the existing category illustration is shown instead. Signed-in users continue directly to the map.

Providers can mark published listings unavailable in My listings and make them available again. Spaces can be marked occupied; these listings remain visible but cannot receive requests. Vehicle and service requests include inclusive start and end dates. Accepted date ranges are shown on the listing and cannot overlap another accepted request; cancellation releases the dates. Older requests without an end date only block their recorded start date, so providers should arrange any additional days directly.

Administrators can open a user's listings from **Users** to temporarily lock an account until a chosen time, disable it until restored, or restore access early. A fixed reason is required and changes are recorded in the access history. Administrator accounts cannot be restricted from this screen. Restricted providers' published listings remain visible but unavailable for new requests; existing requests are not cancelled, and the provider's own availability setting is unchanged. Existing API tokens and remembered logins are revoked when access is restricted. An active browser session is signed out on its next request during the restriction.

Users can request a password-reset link from the sign-in page. Administrators can also send a reset link to the account's registered email from the user's listings page; sending or completing a reset does not restore restricted access. Both flows are rate limited and require working email delivery.

Signed-in users can report a provider from their profile or listing, or report the other person from a request. Reports are private to administrators. In Account reports, an administrator can dismiss a report or confirm it with a chosen deduction and review note. Confirmed deductions are limited to the target's current trust score; reversing a decision restores the points actually deducted. Existing scores are unchanged until a decision is made, and accounts at zero cannot be reduced further.

Every account has a public profile at `/providers/{user}`. Signed-in users can like another account once and remove their like later; the total and the names of people who liked a profile are public. Administrators cannot add profile likes, but can remove any likes they previously made. Likes do not affect trust scores. Profiles also offer reporting for signed-in visitors; neither action is available on one's own profile. Request cards link to the other participant's public profile.

Administrators can filter account reports by submission dates, reporter or reported account name or email, the reported account's current trust score, deducted points, and the last reviewing administrator. Date and numeric bounds are inclusive. Deduction filters include confirmed and reversed reports; a reversed report retains its original deduction in its history. Status tab counts show all reports, independent of filters.

The admin dashboard shows the current pending-report backlog and report submissions over the selected period. Admin analytics shows submission trends, current all-time report statuses, and review decisions in the selected period. Review decisions count events, so one report can be counted once when confirmed and again if later reversed.

My listings shows detail views during the last seven days and the number of people who currently save each listing. Repeated detail views from the same visitor within 30 minutes count once; owner and admin views do not count. Space views reuse the existing view history. Vehicle and service view history starts when this feature is deployed, so earlier activity is not included.

Dialog scrollbars are visually hidden while their content remains scrollable. The page scrollbar is also hidden on narrow screens and in installed PWA display modes; scrolling is not disabled.

Explore offers Carousel, List and Swipe views for spaces, vehicles and rakets. Swipe fills the available map area with one listing at a time; horizontal swipes, arrow buttons or keyboard arrow keys browse without saving or dismissing anything. List uses the available height and scrolls through all results on the current page. Use the page controls for additional results and **Map** to return to the map. Listing previews, map selection and comparison remain available, and the view preference is stored in the browser.

Directions on listing details and Explore cards show either a driving or walking route to the listing's saved coordinates, with estimated travel time and distance. Users can use their current location, select a point on the map, or enter coordinates; the starting point remains marked even if routing fails. Browser location permission is requested only when selected, and the marker is a snapshot rather than live tracking. The origin and destination are sent to openrouteservice for routing and are not saved by Aadi. Routes are estimates, do not reflect live traffic or a moving vehicle/provider, and may be unavailable for some locations. Driving and walking are separate routes; automatic mixed-mode routes and parking selection are not supported. Set `OPENROUTESERVICE_API_KEY` in the server's `.env` and refresh Laravel's configuration cache after changing it. The key must not use a `VITE_` prefix.

### Live messages and notifications

To enable Pusher Channels, set `BROADCAST_CONNECTION=pusher` and `PUSHER_APP_ID`, `PUSHER_APP_KEY`, `PUSHER_APP_SECRET`, and `PUSHER_APP_CLUSTER` in the server `.env`. Keep the secret server-side; the app shares only the public key and cluster with signed-in browsers. Refresh Laravel's configuration cache and restart the web and queue workers after changing configuration. A queue worker (for example `php artisan queue:work`) must run continuously when using the database queue; monitor failed jobs and worker health.

Only authenticated users can subscribe to their own private channel. Pusher receives a refresh signal, not message or notification contents; the browser reloads those from authenticated Aadi endpoints. Updates are queued after database commits. If the connection is unavailable, the inbox checks periodically and the notification bell retains its existing polling. Pusher delivery and live updates require a working queue, network, and valid Pusher credentials.

The Flutter app is a separate repository and was not changed; it should apply the same rules (open on the map after sign-in, offer dashboard/listing tools only when a provider role is `approved` in the user's `providerRoles`).

## Listing requests

Signed-in customers can request a property viewing with a preferred date and time, or a vehicle rental or service with a preferred start date. Fictional seeded sample listings cannot receive requests. Property owners can specify a minimum stay in months and additional contract rules; vehicle owners can indicate whether a driver can be requested. Vehicle prices are per day; duration, driver availability and any extra charge are agreed directly. Times for viewings use the application's configured timezone, shown in the form and requests page.

Requests appear in the Inbox at `/requests` for both parties; `/messages` and individual message-thread URLs remain available. The provider can accept or decline a pending request, and either party can cancel a pending or accepted request. Request submission and acceptance each require consent to share account email and phone with the other party; these contact details are shown only while the request is accepted. A phone may be absent. Notifications are in-app only. A request does not reserve inventory, prevent overlapping requests, collect payment or create a lease. Payment and all further arrangements occur directly between the parties; there is no online payment. Listing records and their requests are separate from the legacy mobile property-viewing API; Flutter does not yet support these new requests.

Signed-in users can message a provider from an active, available, non-sample listing. Each buyer and provider have a separate conversation for each listing. Both participants can find it under **Messages**, reply, and receive in-app notifications. Threads update live when Pusher is connected and refresh periodically otherwise. Conversations remain available if a listing is later deleted or becomes unavailable, but new conversations cannot start from unavailable listings. A restricted account cannot receive messages. Messaging does not automatically share email or phone, and the web messaging feature is not available in the Flutter API. Apply the listing conversations migration before using it.

Request cards link to the current listing when it is visible to the viewer. Deleted listings and inactive listings not owned by the viewer are marked unavailable; the request history remains accessible.

Everyone can open **Calendar** from account navigation or Requests. Accepted requests appear automatically for both parties on their requested date; pending, cancelled and declined requests do not. Personal events and optional notes can be added, edited and deleted and are private to their creator. Dates and optional times use the application's configured timezone. Date-only requests do not imply a duration. The booking form offers a calendar and native date input, but neither personal events nor requests block dates or guarantee availability. Apply the `calendar_events` database migration before using the calendar.

`/dashboard` is the authenticated user's overview. It counts only that user's non-deleted marketplace listings, including drafts, and shows their latest four listings and provider role statuses. `/admin/dashboard` remains separate. Explore keeps its public navigation. Dashboard, profile, listing management, and listing forms share the account sidebar, header, typography, and page heading.

### Provider rentals and jobs

Approved providers can open **Rentals & jobs** at `/provider/records`; regular users cannot access it. Records and payments are scoped to their provider and an approved role for the relevant category. My listings links to a filtered view for each listing. Accepted vehicle and service requests create scheduled records; accepted property viewing requests create viewings, not tenancies. The migration imports existing accepted requests on the same basis. Providers can explicitly record a tenancy from a viewing or by entering the email of a registered Aadi user and selecting their own property. An open-ended tenancy remains current until the provider sets an end date or completes/cancels it.

Providers can record agreed amounts and partial payments in PHP, payment dates, optional notes, and a required period label for rent. Voiding preserves an entry in the history. Use the same label for partial payments for one period. Period totals are compared against the **current** agreed rent; the system does not preserve historic rent rates or create missing periods, dues, invoices or reminders. Payment information is private to the provider, manually entered, and not collected or verified by Aadi. Calendar adds provider-only tenancy periods; accepted vehicle/service requests continue to use existing calendar entries. Cancel a request from Requests so both parties are notified and its booked dates are released. Recording a tenancy does not automatically change listing availability.

When either account is permanently deleted, CRM records and payments are copied to a read-only archive for six months from that deletion; the customer name, listing details and payment notes remain identifiable. The provider can view retained history only while their account and relevant approved role remain active. If the provider account is deleted, retained history is no longer accessible in the workspace. A subsequent account deletion does not extend an existing archive's deadline. Archives are excluded from active counts and calendars and removed by the daily `aadi:process-account-deletions` job; access ends at the deadline even if the job is delayed. Deploy the archive migration and configure and monitor the scheduler. Review the privacy wording and applicable retention obligations before launch. The separate Flutter application and legacy API do not implement this provider workspace.

My listings stays on the account page even when the user has no listings or approved provider roles. Its empty state links to applications instead of redirecting unexpectedly.

## Browser drafts

Pinia manages Explore's search form and comparison selection while Inertia and the URL remain authoritative for applied filters and server results. Comparison selections are cleared when leaving Explore.

Listing create/edit and provider application forms save partial, unsubmitted drafts to browser local storage. Drafts are separated by account, service and (for edits) listing ID. Returning to a form offers **Restore draft** or **Discard draft**; a warning appears if the saved fields or provider application revision changed on the server. Saving the form successfully removes its browser draft. An account change while a form is open requires a reload.

Listing drafts include the title, description, type, price, status and vehicle details, but not location, photos, contract rules, minimum stay or driver availability. Provider drafts include the area, description, applicant type and offering details, but not name, business name, phone, documents, document selections or confirmation. Re-enter omitted fields after restoring. The provider form's server-side **Save draft** remains separate and can retain additional application information.

Browser storage is not encrypted or private from other people using the same browser profile. Free-text fields may contain personal information, so avoid entering sensitive information in drafts on shared devices. Drafts remain on that browser until discarded, successfully saved, or browser storage is cleared. If storage is unavailable, the form reports the problem and can continue without browser drafts; form data then does not survive a reload.

## Contact, locations, and verification files

Profile and provider application phone fields offer international country codes, defaulting to the Philippines. New input accepts digits only, preserving leading zeroes; pasted international numbers can select their country automatically. Existing saved numbers remain unchanged until edited. Choosing a country and entering a number saves an international-format number when it can be parsed; provider application contact information remains separate from the profile contact shared after a listing request is accepted.

Onboarding, profile, provider application, and listing location forms use a city selector backed by the bundled Philippine city directory. Street addresses and service-area details remain manually editable; the directory is served locally, not sent to an external address API. If it cannot load, users can enter the location manually. Existing city values not in the directory remain selectable. Selecting a listing city does not set the map pin, which must be checked separately. In verification forms, select **Add document**, choose its type, then select a file; each file is uploaded when the application is saved or submitted. Finish or cancel an in-progress selection before continuing or saving. Previously saved private documents and newly selected files are shown separately. Removing a saved document is applied only when the application is saved; it can be restored before then.

In-app toasts report server success and validation failures and can be dismissed. They appear at the lower right on desktop and as a top-centered snackbar on mobile, with an icon for success or error. Verification email feedback uses the same component, including when a modal is open. They use ordinary web UI and safe-area offsets, not native webview APIs; error details remain available inline.

## Photo contract

The existing canonical marketplace `photos` array is an ordered gallery of up to 12 image URLs. `photos[0]` is the featured photo. Selecting **Set as featured** moves that photo to index zero; removing it promotes the next photo. Zero photos remains valid for existing listings and drafts; the UI shows an illustration fallback.

The web form uploads photos through `/listing-photos`, then sends the ordered array with the usual listing create/update request. Existing marketplace API clients should send the featured URL first. Property records store `photos`; vehicle and service records store `images`; Marketplace maps all three to `photos`. This change does not migrate the database, duplicate image files, or add a competing featured-photo field. Removing a photo from a listing does not delete the underlying uploaded file.

Full details display the ordered gallery with previous/next controls and selectable thumbnails. The featured photo is initially selected. Guest preview modals continue to show only the featured image.
